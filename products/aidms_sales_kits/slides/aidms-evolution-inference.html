工具結果回到任務狀態，觸發下一輪模型呼叫。

跨輪次管理

Context、session、進度保存、錯誤恢復與執行限制。

品質判定

Trace、任務成功率、工具結果驗證與人工介入。

概念參考：Anthropic：Effective harnesses for long-running agents。

此處是通用架構整理，不代表 AIDMS 已提供 Agent Harness。模型可輸出 tool call，但實際工具執行與授權通常由 harness 負責。一個任務可能呼叫模型多次，推論速度只是任務完成時間的一部分。

02 · INFERENCE ENGINEERING

推論請求五步驟：各元件的責任分工

步驟負責元件工作內容
1. Client應用程式／Agent Harness組合 prompt、對話歷史與參數，呼叫模型 API。
2. GatewayAPI Gateway／反向代理身分驗證、限流與統一入口。簡單部署可直連 vLLM。
3. Router負載平衡／模型路由元件
未來可整合 llm-d Router		選模型與 worker，負責跨 worker 分流。
worker 內部的排隊與批次排程由 vLLM 處理。
4. WorkervLLM載入模型，執行 Prefill／Decode、KV cache 管理、batching 與 token 生成。
5. OutputvLLM 產生回應
Client 接收與呈現		vLLM 輸出文字／API 串流，gateway 轉送，應用或 Harness 顯示或繼續處理。

AIDMS 管理 Project 資源、User、節點與 vLLM Job 的生命週期。
這五項是功能分工，不必部署五套軟體。

依使用者參考圖整理。vLLM 文件 ／ llm-d 架構。Gateway／Router 按方案配置，未確認 AIDMS 已內建。

Client 通常由應用或 Agent 團隊負責。Gateway 與 Router 通常由平台團隊整合，也可以由同一套元件提供。只有單一模型服務時，不一定需要獨立的跨 worker router。

vLLM 通常同時承擔 Worker 與 Output 的伺服器端工作，包括 Prefill、Decode、KV cache、內部排程與串流回應。實際工具執行仍由 Harness 負責。引擎機制已提供，但效能需依模型、GPU 與併發量調校。

AIDMS 是管理控制面，不代表每筆推論請求都需經過它。未來 llm-d 可提供模型感知的跨 worker 分流，其具體整合範圍仍待確認。

02 · PERFORMANCE

速度、容量與任務品質有不同指標

觀察層級代表指標回答的問題
使用者等待TTFT、ITL／TPOT、E2E latency多久看到首字？後續輸出是否順暢？
推論服務Tokens/s、queue、KV cache、goodput在延遲目標內能服務多少請求？
基礎設施GPU 使用率、記憶體、節點／Job 狀態資源是否足夠？工作負載是否健康？
Agent 任務成功率、工具錯誤、總時間、總成本Agent 是否正確完成任務？

GPU 使用率高，不必然代表使用者等待時間短或 Agent 任務成功。

依參考圖整理。AIDMS 的基礎操作觀測有 API 依據，推論 SLO 與 Agent 評估整合仍需另行確認。

TTFT 是請求到首個輸出的時間，含排隊等開銷。ITL 描述相鄰輸出間隔，TPOT 為首 token 之後的平均每 token 時間。Goodput 是符合目標 SLO 的有效服務量。不要把平台已有 Grafana proxy 說成已完成全部推論指標整合。
